# NocoCRM overview and conventions

Read this before any change to NocoCRM: where the specification lives, the languages code and copy use, the navigation and settings, record links and drawers, phone numbers, the business time zone, field lengths, and the sign-in pages.

Code is written in English: comments, identifiers, literals and the prompts sent to the model. Chinese appears only in translation files — `client/locales/`, `server/locales/` (the AI's labels, headings and conversation titles in `server/locales/crm-ai/`, Chinese first and English second, picked by the AI language setting), the deployment's sales guidance (beside its English version), the demo dataset and the geography names — and in input matching that has to recognise Chinese (a company's legal suffixes, an extension written 转 or 分机); applied migrations are history and stay as they were.

This application implements its specification, `nocosolution/NocoCRM/SPEC.md` (in the optional NocoSolution clone; edit it with targeted replacements only, never a formatter), in `client/pages/crm-*.tsx`, `client/components/crm/`, `server/providers/crm/`, and `server/routes/crm.ts`. Navigation is declared in `client/routes.ts`: the overview, the inbox, tasks and approvals lead the menu without a heading (the former Action group is gone), the CRM's other pages sit in menu-only groups (Records: leads, opportunities, companies, contacts, then reports; Integrations; Agent team: Auto follow-up, the CRM's four agents on one page, Business guidance, then the Agents plugin's Agents, Skills, Models and Usage), and the application layout's sidebar renders such a group as a labelled `SidebarGroup` with its children always visible (`NavigationMenu`'s `sections` option in `client/layouts/components/navigation-menu.tsx`, an application change to the template's menu), instead of the template's collapsible sub-menu or, collapsed, its popover; and last comes Settings, one entry (`settings` at `/settings`, `client/pages/settings/index.tsx`) whose page holds the pages that configure the CRM as tabs (`LinkTabs` in `client/components/crm/link-tabs.tsx`, which Auto follow-up's tabs use too), at the addresses they had as entries of their own, each tab's route keeping its grant and each tab shown only to whoever it lets open it, `/settings` opening on the first of those; the page draws the title and the tabs, which stick to the top of the layout's scrolling column with a band of the page's ground under their rule, and the tabs' pages keep their description and actions, which `PageHeader` draws on a row under the tabs, its `PageContainer` starting closer to them (`PageFrameContext` in `client/components/page-frame.ts`, an application change to the UI Library's `PageHeader` and `PageContainer`, which `RouteChildPage` clears, so a covering page such as a permission set's draws its own heading) (General at `/settings/crm`, 通用, its business defaults, reminders and demo dataset one card under another, the first two each saved by its own card's Save, which sends that card's settings alone and is offered once one of them changed, `?section=<card>` bringing a card into view; the administration pages the plugins stopped shipping, rebuilt on their APIs in `client/pages/settings/`: Users (`/settings/users`, the users plugin's `UsersClient` with the CRM's role scope, gated by its `user` record type, which only root holds), Permission sets (`/settings/permission-sets`, each set a covering page with Permissions and Members tabs, the Permissions tab the UI Library's `PermissionEditor` over the authorization plugin's catalog with the Pages section filled from the route tree, `useRouteTree` in `client/routing/route-context.tsx`, and a save that refuses a set changed since it was loaded), API keys (`/settings/api-keys`, each person's own keys, open to everyone) and Scheduled tasks (`/settings/scheduled-tasks`, the scheduler's schedules with their runs, gated by the page grant `scheduler.schedules` its API checks); their copy is `admin.*` in `client/locales/crm/admin.ts`, their shared components in `client/pages/settings/shared.tsx` and functions in `hooks.ts`, and the assistant's dock is hidden on every `/settings/...` page; the Agents plugin's pages, at the paths the plugin navigates to, `/agents`, `/skills`, `/models`, `/usage`, are in the Agent team section above it), there being no settings area since template 1.0.0-beta.60, and each entry shows only to whoever its grant lets open it; the sidebar keeps its 16rem width; the brand (`client/layouts/components/app-brand.tsx`) shows the NocoCRM wordmark.

The header (`client/layouts/components/header-actions.tsx`) has no inbox button: the template's (`InboxHeaderButton`, which replaced the CRM's own bell and notification centre in template 1.0.0-beta.56) was removed with `client/components/inbox-button.tsx`, the inbox an entry of the menu's own, right under the overview, instead; the header and keeps the settings link on every surface, marked while settings are shown.

The layout's main column carries the `crm-page-main` class so the assistant panel pushes header and page together, by exactly its 28rem and only from 1280px (`client/styles.css`); it starts closed on every screen (narrower ones show it over the page),. The sign-in pages and the layouts are the template's, translated through the template's own `auth.*`, `status.*`, `shell`, `surface` and `settings` locale keys; the application's own wording lives in the `crm` namespace, `app.title` and `navigation.home`.

A detail page opens the records it links to in a drawer over itself (`client/components/crm/record-drawer.tsx`, state in the `?open=entity/id` query parameter kept by `useRecordDrawerState`, content rendered by the same detail components through `RecordDrawer` in `client/pages/crm-detail.tsx`); the workspace hosts the same drawer for its task and approval cards, loading `RecordDrawer` lazily on the first open so the detail pages stay out of its chunk.

Phone numbers are kept one way (`normalizePhone` in `server/providers/crm/phone.ts`, no imports so the browser may take it): a Chinese mobile as its 11 digits, a Chinese landline as area code, hyphen and number, a number abroad as + and its digits, an extension after a hyphen; `CrmService.save` applies it to every `phone` field, the AI capture to what it fills, and the list search to a typed number as well as the text; `202610030001_crm_phone_numbers` normalised the numbers kept before, with the rules copied into it. The business time zone a CRM starts with, and the one the pages read until the settings have loaded, is US Eastern time (`DEFAULT_TIME_ZONE`, `America/New_York`, in `server/providers/crm/zone-time.ts`, which every fallback takes); a deployment sets its own on the settings' General tab. Field lengths are set once in `server/providers/crm/limits.ts` (255 characters on one line, the width of the text columns, which SQLite ignores and PostgreSQL and MySQL enforce; 30,000 in a long text; 100 items in a list), which `CrmService.save` enforces and the form and inline editors take as their inputs' `maxLength`; it has no imports, so the browser bundle can take it. Record names are drawn through `RecordLink` in `client/components/crm/common.tsx`, which cuts a long name with an ellipsis after one line (two, `lines={2}`, on the board's cards) and shows it whole on hover, so no name wraps into the layout around it, and draws no arrow after it (no link in the CRM does) and no underline under the pointer, only the primary colour, as the settings pages' names in their lists; draw a record's name through it rather than a bare link. Record links take their props from `useRecordLink`, which falls back to plain navigation where no drawer is provided; every list page's table and board, and the task list, host one (`DrawerHost` in `client/pages/crm-list.tsx`), so the records a row, a card or a task links to (a contact's company, a task's deal) open over the list, while the row's own name still opens its page (its `RecordLink` under `RecordDrawerContext.Provider value={undefined}`), as does its empty space (`openOnRowClick`).

The Vitest configuration resolves the installed `@nocobase/app-client` package rather than the template monorepo alias, so component tests work in this standalone checkout.

Tailwind lists plugin files when Vite starts, so restart `pnpm dev` after installing a plugin, or its classes are missing until then.

See `README.MD` for running the application, demo data, configuration and deployment.

The sidebar's footer (`client/layouts/components/sidebar-footer.tsx`) shows the application's name and version from what the server publishes, `app.displayName` and `app.version`, read from the `package.json` beside the running server, and otherwise from the `package.json` the client was built from (its two fields alone, inlined by Vite), because a host that starts the application elsewhere, as NocoBase Studio's app host does, publishes neither and the footer read v0.0.0.

The company menu checks Better Auth sign-out results before refreshing the session and shows a localized error toast for API or network failures. Preserve this behavior when upgrading the layouts; navigation alone does not revoke a session.

The authorization provider clears the permission snapshot before rendering a new session. Route navigation and page guards subscribe to the authorization revision; preserve these checks when customizing the layouts so account changes and permission updates take effect without a reload. Pending checks hide protected content, and failed checks deny access.

Navigation groups retain their expanded or collapsed state while the navigation tree stays mounted. Selecting a new page expands its ancestor groups without collapsing other groups; users can still collapse the active group manually. Keep this behavior in the application's navigation.

Authentication pages are not plugin-owned: `/login`, `/forgot-password`, and `/reset-password` are application routes declared in `client/routes.ts`; the CRM has no `/register` route and turns the sign-up endpoint off (`emailAndPassword.disableSignUp` in `server/config/auth.ts`), because accounts are created on the Users page, and its login page (`client/pages/auth/login.tsx`) links to registration only while sign-up is on, which it is not, and to the forgot-password page only while the authentication plugin reports self-service reset available (`usePasswordResetCapability`, from `GET /api/authentication/capabilities`, true only with a reset mail configured), as template 1.0.0-beta.64 does, the forgot-password page itself saying so when it is not; the template's `/device` page, which approves a CLI's sign-in, stays.
