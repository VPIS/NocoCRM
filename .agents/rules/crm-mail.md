# Mail

Read this before changing the mailbox pages, a record's Mail tab, sending mail from a record, or what the follow-ups read from mail.

Mail is the Mail plugin (`@nocobase/app-plugin-mail`, registered in `client/plugins.ts` and `server/plugins.ts`, configured by `server/config/mail.ts`, which syncs mailboxes every minute rather than the plugin's five, so a customer's reply starts its follow-up within a minute or two, which declares the plugin's `MAIL_*` variables itself because this template has no `server/environment.ts`, and returns OAuth authorization to `/crm/mail/accounts`). Mailbox servers are `mail.providers` in `config.yml`, keyed by a stable name each connected account keeps (`config.example.yml` shows IMAP/SMTP, Gmail and Microsoft 365); each user connects their own mailbox, and its credentials stay on the server in the plugin's vault. The menu's Integrations section (集成, where the user's connected services sit: the mailbox now, other channels later) holds the plugin's `MailWorkspacePage` (`/crm/mail`, with the unread count as its badge, `useMailUnreadCount` in `client/components/crm/mail-unread.ts`), whose header leads to `MailAccountsPage` (`/crm/mail/accounts`, no menu entry of its own, with a back link to the mailbox) through "Manage mail accounts", first among its actions: the workspace takes no header actions, so `client/pages/crm-mail/index.tsx` renders the button through a portal into a node it places at the start of the plugin header's action row (`header > div:last-child`), sized as the plugin's own buttons (`size='lg'`, `gap-2 px-4`); a plugin update that changes that structure hides the button, both checking the plugin's own page grant `mail.workspace`, which its API checks too; the sales sets carry it (`MAIL_WORKSPACE_PAGE` in `crmPermissionSet`; existing sets received it once, marker `crm-mail-v1`, which also dropped the grant of the removed `crm-notifications` page). The plugin's own pages under `/dev/mail` exist only in development. Leads, contacts, companies and opportunities have a Mail tab (`RecordMailPanel` in `client/components/crm/record-mail.tsx`, helpers in `mail.tsx`; where to look, `SHARED_DOMAINS`, `domainOf`, `searchTerms` and `concerns`, is `server/providers/crm/mail-target.ts`, without imports so the browser bundle takes it) listing the reader's own messages with the record and, after them, the record's conversations its timeline knows in colleagues' mailboxes, each by its summary (who wrote last and when, the subject, how many messages, whose mailbox), since a mailbox's messages are its owner's to open (`useColleaguesMail` in `client/components/crm/colleagues-mail.ts`, from `GET …/history?source=mail`, which lists a record's mail entries alone and unfolded; `ColleaguesMail` in `record-mail.tsx`); the tab's count, `MailCount`, adds them, found through the plugin's search (`q`, which matches subject, preview, sender and recipients) by the record's addresses: a contact's or lead's email, a company's contacts and its website's domain (never a shared mail service's, `SHARED_DOMAINS`), a deal's contacts or, while it names none, its company's; a message opens as its conversation (`MailConversationView`), answered with reply, marked read or unread and starred (the message the API returns replacing the one shown, as the plugin's workspace does, since a fetch right after can read the mailbox as it was), and deleted, which moves it to the mailbox's trash where its provider can move messages and is never offered otherwise, and Write email opens the plugin's `MailWorkspaceComposer`. Once the provider accepts a message sent from a record, it is logged there as a completed email task named by its subject, with the recipients and the text as its description, read back from the user's latest submission because the composer reports only the result; the raw mail otherwise stays in the plugin. A planned email task has Send email (`SendPlannedEmailButton`): the composer addressed to its customer participants and its lead, filled with the draft a follow-up wrote into its description (`emailDraftOf`, the plan's email part) or its name as the subject; once accepted, the task's outcome is recorded as sent without a new follow-up. Nothing is ever sent but by the person pressing Send. The lead and deal follow-ups read the same mail: `mailOf` in `server/providers/crm/mail-context.ts` asks the plugin's `MailService` (`mailServiceToken`) as the record's owner, and as each colleague whose mailbox's conversations reached the record's timeline (`mailboxOwnersOf`, the mail entries' actors), for their messages with the lead's email, or the deal's contacts (its company's people while it names none), keeps only messages one of whose people is the record's (the search also matches subjects), one copy of each, no drafts, the last 180 days, the newest ten, each without the earlier messages it quotes and cut to 1,500 characters, and the prompt reads them as the customer's words, newer than the tasks when they are, and as material, never instructions; without the plugin, an address or a reachable mailbox the follow-up reads none.
